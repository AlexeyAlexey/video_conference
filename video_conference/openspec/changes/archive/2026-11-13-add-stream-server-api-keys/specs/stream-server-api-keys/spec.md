# Spec Delta

## Purpose

Issues and manages API key credentials that belong to individual stream
servers in the stream server admin portal, so each physical server can
authenticate with the portal (for example to fetch a public key by app id
and public key id, or to push its current state).

## ADDED Requirements

### Requirement: Stream server API key record

The system SHALL persist each stream server API key in the portal database
with a UUID primary key, a required non-unique `name`, an optional
`description`, a unique `prefix` holding the secret's
`env_prefix <> "_" <> prefix_id` lookup prefix (`"ssak_"` followed by a
generated id), a secret stored only as a hash, a required `stream_server_id`
association to a portal stream server, an `enabled` flag defaulting to true,
a `lock_version` integer defaulting to 1, and timestamps. Key names SHALL
NOT be unique. The hashed secret SHALL be unique within one stream server.

#### Scenario: Creating a key

- **WHEN** a stream server API key is created with a name for a chosen stream server
- **THEN** the record is persisted with the given name, `enabled` true by default, and `lock_version` 1

#### Scenario: Duplicate key name allowed

- **WHEN** a stream server already has an API key named "node-agent"
- **THEN** creating another API key named "node-agent" on the same stream server succeeds

### Requirement: Optimistic concurrency for stream server API keys

Every update of a stream server API key SHALL be guarded by the record's
`lock_version`: the write succeeds only when the persisted `lock_version`
still matches the version the caller loaded, and a successful write
increments it. A write attempted against a stale record version SHALL fail
and report the record as stale through the normal error channel — it SHALL
NOT raise an unhandled exception.

#### Scenario: Stale update rejected

- **WHEN** two admins load the same API key and both submit updates, the second write using the outdated `lock_version`
- **THEN** the second write fails with a stale-record error on the `lock_version` field and the first write's change is preserved

### Requirement: API key secret generation and one-time display

The system SHALL generate a random API key secret when a stream server API
key is created. The plaintext secret SHALL be displayed to the admin
exactly once, immediately after creation, and SHALL NOT be retrievable or
displayed again afterwards.

#### Scenario: Secret shown once

- **WHEN** an admin saves the new API key form successfully
- **THEN** the generated plaintext secret is displayed once with a copy affordance, and is not shown on any later page load

### Requirement: API key secrets stored hashed

Stream server API key secrets SHALL be persisted only as a bcrypt hash.
The plaintext secret SHALL NOT be stored in the database, in logs, or in
any other persistent form.

#### Scenario: Only the hash is persisted

- **WHEN** a stream server API key is created
- **THEN** the database row contains a bcrypt hash of the secret and no column holds the plaintext secret

### Requirement: Shared API key secret generation

Stream server API key secrets and application API key secrets SHALL be
generated by the same shared secret-generation logic, so both scopes use
one implementation for creating and hashing secrets. A generated secret
SHALL have the structure `env_prefix <> "_" <> prefix_id <> "_" <> <random>`
where `env_prefix` marks the scope (`"ssak"` for stream server keys,
`"aak"` for application keys) and `prefix_id` is an independently
generated id.

#### Scenario: Both scopes share generation

- **WHEN** an application API key or a stream server API key is created
- **THEN** its secret is produced by the same generation logic and stored as a bcrypt hash

### Requirement: Stream server API keys page and required server filter

An authenticated portal admin SHALL be able to open a page at
`/stream-server-admin/stream-servers/api-keys` for managing stream server
API keys. The page SHALL offer a required stream server filter whose
searchable options read "name (host)". There SHALL be no option to select
all stream servers; until a server is chosen the page SHALL prompt the
admin to pick one and SHALL NOT list keys or offer adding a key. The
chosen server SHALL be reflected in the page URL.

#### Scenario: Prompt before a server is picked

- **WHEN** an admin opens the page with no stream server selected
- **THEN** the page shows a prompt to select a stream server, lists no keys, and the add action is unavailable

#### Scenario: Filtering keys by server

- **WHEN** an admin picks a stream server in the filter
- **THEN** the page lists that server's API keys and the URL carries the chosen server id

#### Scenario: Key prefix shown

- **WHEN** the page lists a server's API keys
- **THEN** each key row shows its `prefix` in an API KEY column with a copy affordance

#### Scenario: Searching filter options

- **WHEN** an admin types in the filter's search field
- **THEN** the stream server options are narrowed by the typed text

### Requirement: Stream server API key management

An authenticated portal admin SHALL be able to add an API key for the
filtered stream server through a modal whose form shows the server
read-only as "name (host)" and accepts name, description, and enabled.
The admin SHALL rename a key, edit its description, and toggle its enabled
flag through per-field controls — there SHALL be no whole-row edit form
and no delete action. Validation errors SHALL be shown inline.

#### Scenario: Adding a key through the modal

- **WHEN** an admin with a stream server selected activates "Add API key" and submits a valid form
- **THEN** the key is created for the filtered stream server and the one-time secret is displayed

#### Scenario: Renaming a key

- **WHEN** an admin activates the rename control on a key row and saves a new name
- **THEN** the key's name is updated

#### Scenario: Editing a key's description

- **WHEN** an admin activates the description control on a key row and saves
- **THEN** the key's description is updated

#### Scenario: Toggling enabled

- **WHEN** an admin clicks a key's enabled checkbox
- **THEN** the enabled flag is persisted immediately to the opposite value

### Requirement: Responsive stream server API keys page

The stream server API keys page SHALL be usable on mobile, tablet, and
desktop viewports. Its data table SHALL scroll horizontally inside its
container rather than overflowing the page.

#### Scenario: Narrow viewport

- **WHEN** an admin opens the page on a viewport below the desktop breakpoint
- **THEN** the layout stays usable and the keys table scrolls horizontally within its container
